# Cart, topup and wallet checkout

## Invariants
The existing `mirpanel_community.wallet_accounts` and immutable `wallet_ledger` remain the sole wallet source. Amounts are integer qəpik. Topups have no sale/order and do not earn membership spend. Only the verified owner-admin gateway can decide a topup. A row lock, deterministic ledger request key and one transaction serialize approvals. A request may be approved once, with the explicitly confirmed amount, or rejected without credit. Reasons are generated by the server.

The browser cart persists product IDs, plan indices and quantities in localStorage; no login merge duplicates it. No stock is taken by cart additions or quote requests. Prices are resolved from the server catalog and the existing account-specific price table. Fixed account prices replace final catalog prices rather than stacking discounts. A new checkout freezes each unit's price. Active reservations and old orders are not repriced.

Checkout groups and per-unit lines reference the existing payment reservations and orders. Card carts use the existing inventory/payment RPC, with its stock and payment-card capacity rules. All units reserve in one PostgreSQL transaction, or none reserve. One private receipt is shared by the related orders. Submit, account/browser ownership links, immutable price metadata and all cart lines are atomic and idempotent. A selected file is never payment confirmation. Only an explicit Davam et action submits and proceeds to the existing WhatsApp URL; no message is sent by this application.

Wallet checkout creates existing-format reviewing orders, links inventory reservations and debits the wallet in the same transaction. Insufficient funds rolls back every order and reservation. Payment confirmation is distinct from delivery: stock remains RESERVED until the existing admin completion mechanism. A server trigger refunds the original paid line amount once on rejection/cancellation, while existing inventory triggers release stock. No supplier or automatic delivery is invented.

## Access and receipt safety
Guest purchases remain enabled. Wallet/topup APIs require a verified, nonblocked account resolved from the server session, never a submitted account ID. Cart capabilities use the existing signed Secure/HttpOnly browser cookie and check account ownership on every applicable operation. Proxies forward only the allowlisted account/browser cookies, not admin authorization. Mutations require the allowed origin. Private receipt views are signed for 60 seconds after authorization.

JPG/PNG/PDF bytes pass the existing isolated safety decoder and 5 MB limit. OCR/content detection stays off. Storage is verified before success. Retry does not mark an unconfirmed file successful. Existing receipt retention settings apply: shared cart receipts stay until every linked order is eligible; abandoned/replaced uploads are boundedly cleaned after the staging grace period. Topup review receipts are not prematurely deleted.

## Schema/release
Files: `mirpanel-admin/community/shop-{migration,verification,rollback}.sql`.
Run `node scripts/public-community-backup.mjs --shop` first. It creates a restricted DPAPI-encrypted external dump, restores it separately, compares preserved data fingerprints, applies the migration twice, verifies it, and exercises the nondeleting rollback. No production rows are copied into the synthetic functional test database. The restricted restore is exclusively for backup validation.

`node scripts/wallet-release.mjs --shop` refuses a stale/mismatched/unverified backup, then applies the migration. `node scripts/wallet-release.mjs verify --shop` must yield six true checks. Deploy this app only after verification. No test accounts, orders, wallets, topups, receipts or methods are seeded into production by the migration. The internal inactive/archived bookkeeping method is created only as part of a real wallet purchase transaction; it is never offered as a transfer card.

Rollback sets `shop_release.enabled=false`, without deleting or rewriting wallet/order/history data. Keep the compatible receipt cleanup/refund code running for existing new orders. Do not restore obsolete positive-only ledger or unique-receipt constraints over legitimate new records, and do not blindly redeploy an old receipt-cleanup implementation.

## Test scope
`test-shop-postgres.mjs`: real isolated PostgreSQL and real existing inventory/order RPCs; multi-item, zero/finite/unlimited, account prices, insufficient balance rollback, concurrent last unit and concurrent wallet spends, repeated approval/rejection, zero-price order completion, refund once, immutable ledger, retention.

`test-shop-browser.mjs`: browser → HTTP API → real isolated decoder → private local file storage → real PostgreSQL orders. JPG, PNG, PDF; content is not OCR classified; unsafe/oversize and storage-error cases; guest cart persistence, signed-in persistence, wallet purchase, topup review. This private local storage test is not claimed as a production Supabase write test. Production tests are read-only, with no orders/reservations/receipts/WhatsApp actions.

`test-shop-admin.mjs`: real admin server, owner identity, guest/employee/CSRF denial and synthetic topup approval, with screenshots. `test-shop-proxy.mjs` checks the Cloudflare proxy forwarding contract without network writes. Existing checkout cancellation, upload-only, stock API, public community/profile, wallet and statistics suites are retained.

Promocodes and referral commissions are not added. No Gmail sender configuration or archival queue is changed. External bank settlement still requires human verification.
