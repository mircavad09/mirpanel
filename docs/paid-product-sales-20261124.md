# Confirmed paid product units · 2026-11-24

Root cause: `product_sales_snapshot` was still installed with `delivered-units-v1`. It reads the customer delivery ledger; a confirmed payment waiting for fulfillment does not appear. Read-only production comparison found seven missing units in seven orders (Canva 2, CapCut 1, Netflix 1, Spotify 1, Zoom 1, MirPanel Token 1). All seven were created after the last baseline edit, 2026-11-17 18:21:18 Asia/Baku. Therefore they can be added without interpreting the historical baseline coverage.

`confirmed-paid-units-v2` uses stable order ID + line index + product ID. Quantity comes from the immutable checkout snapshot (legacy single-product orders use the persisted product/quantity). `payment_confirmed` or a persisted Epoint purchase `paid_at` is required for the new paid component, including Epoint payments awaiting stock. Wallet deposits are not product orders and never enter this projection. Rejected/expired/unpaid rows do not enter it. Package names, package order and catalog names are irrelevant.

The projection contains each order line once, with purchased quantity minus only proven refunded undelivered units. A cancellation record alone or a card refund promise does not prove a refund. The existing actual `community_refunds` record must cover the cancellation amount, and line quantities must be present. Delivered units are retained. Repeated callbacks/status changes, automatic/manual delivery, replacement, and reconnect/restart cannot create incremental sales rows; concurrent actual purchases both appear in the next consistent database read.

Historical baseline rows are preserved exactly. The old already admitted legacy component is retained by order/line rather than reimporting old approvals. There is no recorded covered-through date in the October 14 initialization/edit or November 14/17 edits. The 3,524 legacy inferred units remain explicitly labelled uncertain; no cutoff, subtraction, remapping by names or additional historical increments are invented. Deleted old IDs remain separate, even when names resemble current products. The initializer's original 10,000 is now 10,001 after the separately approved Free Fire baseline correction on November 17; this task never changes it.

All views read the same API. Transactional statement triggers advance a presentation revision on relevant order, refund, delivery, Epoint paid and baseline changes. Each process checks that revision before serving its coalesced snapshot; therefore an existing 10-second snapshot cannot survive a committed sale/refund. The visible browser refresh cycle remains 10 seconds, with return/focus refresh, no-store HTTP and error preservation. `+` formatting is consistent. Revision triggers never modify orders, balances, fulfillment, inventory or monetary ledgers.

Startup installs the versioned projection once; installation is advisory-locked and repeatable. The older cart installer recognizes the retained compatibility marker and cannot replace the paid reader. Public roles have no table/function access except the existing authenticated server path. Admin permissions are unchanged.
