# Product payment method groups

The payment selector now shows Kart (Bank kartı), Balans (the authoritative customer balance), and Apple Pay (Tez ödəniş) when the existing iPhone/Apple readiness rule allows it. Other supported methods are inside the native, initially collapsed “Digər ödənişlər” disclosure. Google Pay keeps the Android/token readiness rule; Birbank uses its existing signed wallet redirect. m10 is selectable only when the existing server flag and wallet discovery report it available; production remains disabled. Card-to-card and bank-account transfer tiles are disabled and labelled “Hazırda mövcud deyil” and “Tezliklə”. No Portmanat, separate Kapital Bank or duplicate Apple Pay method exists.

All payment tiles have the same grid width and 128px height, official existing wallet artwork, and yellow selection border/check. Unsupported Apple/Google methods are not mounted. Changing a radio or expanding the disclosure creates no request or navigation. The existing legal checkbox and required-details/stock checks gate the single “Sifarişi tamamla · məbləğ” button for every method.

Integration contracts are unchanged: `productPaymentChoices({host,el,select,signal,preferDirect})`, radio `paymentMode`, wallet method `wallet`, external identifiers `card`, `apple-pay`, `google-pay`, `birbank`, `m10`. The new `.checkout-primary-methods` container holds the main tiles; `.checkout-other-methods` / `.checkout-secondary-methods` hold the disclosure. The existing quote (`q.items`, `q.totalCents`, `q.balanceCents`), checkout request key, consent, `/api/payments/shop/epoint`, provider status, checkout/order relation and result screen remain intact. Summary work can replace `checkoutLayout` independently while retaining these contracts.

No settlement, wallet writer, signature verification, pricing, stock, merchant fee, preparation or delivery code changes. Existing database regressions verify price mismatch rejection, signed and amount-matched callbacks, pending-attempt reuse across method changes, concurrent opening requests, one wallet debit and direct-purchase separation from wallet credits. Browser fixtures cover Chrome/WebKit at 320/390/430/1440, collapsed groups, disabled alternatives, equal tile heights, consent gates, double clicks and provider navigation; long actual balance, missing details and insufficient stock are also checked. Physical iPhone/Android and real payments are not part of this release's tests. No new provider operation is authorized or created by the verification.
