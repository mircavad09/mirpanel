# Admin top-up reporting

The owner-only `GET /api/admin/community/shop?only=topups` report reads card-to-card requests, Epoint checkout requests and wallet intents. A full join on the existing UUID merges an Epoint checkout and its intent into one display row. Neither report generation nor automatic payment cards invoke settlement, reconciliation, provider APIs or wallet mutations. A successful Epoint row additionally requires its matching committed wallet ledger credit. Staff permissions are unchanged.

Filters: method and all/today/month/custom inclusive Baku dates, using a half-open UTC interval. Completed operations use settlement time; other operations use request/decision time. The full filtered set drives the totals, independently of the 100-row list pages. Unknown historical Epoint methods remain unknown, not card-to-card. Request reference is `mp_ep_UUID`; transaction comes only from the stored provider reference. Creation URLs, secrets, widget tokens and raw provider responses are never selected.

The reporting-only migration creates an immutable Apple Pay tariff: 300 basis points from 2026-11-23 00:00 Asia/Baku, sourced to the owner's dated request. It does not claim provider settlement evidence. Older payments and all other methods have unknown fees unless a fact exists. Integer-cent half-up arithmetic calculates each operation's estimated fee. A later actual fee takes precedence, while the estimated comparison remains visible. No product order payment method, cost/profit report or balance allocation changes.

`topup_finance_facts` is an append-only financial expense/refund journal with unique `(source,event_id)` and the existing operation UUID. It supports explicit AZN fee, refund and fee-refund facts with dated evidence. There is no public/admin mutation endpoint or guessed ingestion from callback fields: current Epoint tables have no actual fee/refund fields. No actual bank cost or refund is invented. Future verified statement ingestion can append evidence once without re-crediting/debiting a customer. Refund totals shown for selected operations are their currently recorded cumulative refunds, including later refunds; they are not a bank cash-flow statement for the refund event date. A full refund does not erase the original completed deposit. The remaining bank inflow subtracts recorded refunds and adds actual fee reversals. Wallet balances are never changed by this report.

Actual and tariff-estimated expense subtotals are separate, with transaction counts; unknown-fee counts are shown, and no full net total is claimed when fees are unknown. This journal/report is the sole location added for the expense; nothing is charged again to product sales. Automatic operations never offer manual approval. Posting their UUID to the receipt approval route cannot create a ledger entry.

Tests: `MIRPANEL_SHOP_TEST_PORT=55489 node scripts/test-admin-topup-finance.mjs` uses disposable localhost databases and synthetic settlement replies. `node scripts/test-admin-topup-browser.mjs` uses isolated fixtures in Chromium and WebKit at 320/390/1440. Existing Epoint result/four-method/checkout regressions remain unchanged. No real provider payment, balance credit or refund is created in verification.
